Welcome to the DevOps side of the house! If you are primarily a backend developer, thinking of this setup like **Java class inheritance** is the easiest mental model:
 * **Cluster Config** is your Parent Class (defines global variables every service defaults to).
 * **Train Config** is your Child Class (extends the parent and overrides specific methods/variables for that specific release train).
 * **Spring Boot** naturally merges them at runtime, where the child (Train) overrides the parent (Cluster).
Since we are using **Harness** and **OpenShift**, the setup spans three places: your **Spring Boot Code**, your **OpenShift Manifests (YAML files)**, and the **Harness UI**.
Here is the exact step-by-step pipeline from start to finish.
## Part 1: Your Backend Code (Spring Boot)
You don't want your Java application to care *where* it is running; it should just look at a folder path and read whatever is there.
### 1. Update your Application Configuration
Open your project's src/main/resources/application.properties (or application.yml). Add this single line:
```properties
spring.config.import=optional:file:/config/cluster/application.properties,optional:file:/config/train/application.properties

```
> **What this does:** When your jar runs in OpenShift, Spring will look into /config/cluster first. Then, it looks into /config/train. If a property (like database.url) exists in both, the one in /config/train **wins** and overrides the cluster one. The optional: prefix ensures your app won't crash when you run it locally on your machine without these folders.
> 
## Part 2: The Infrastructure Configs (OpenShift YAMLs)
In your code repository (or wherever you store your Kubernetes deployment manifests for Harness), you need to define how OpenShift builds these files.
### 2. Define the Train ConfigMap (configmap.yaml)
Create a standard ConfigMap template. We will use a Harness placeholder (<+env.variables.train_properties>) so Harness can inject the correct properties depending on the train.
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: backend-service-train-config
data:
  application.properties: |
    <+env.variables.train_properties>

```
### 3. Update your Deployment Manifest (deployment.yaml)
Modify your Deployment YAML to tell OpenShift to create virtual folders inside your container and attach the ConfigMaps to them.
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-backend-service
spec:
  template:
    spec:
      containers:
        - name: backend-container
          image: <+artifact.image> # Harness placeholder for your Docker image
          volumeMounts:
            # Mount the Global Cluster Config Map to the cluster folder
            - name: cluster-config-volume
              mountPath: /config/cluster
            # Mount the Dynamic Train Config Map to the train folder
            - name: train-config-volume
              mountPath: /config/train
      volumes:
        # Link the folder names to the actual ConfigMap objects in OpenShift
        - name: cluster-config-volume
          configMap:
            name: global-cluster-config # This map is already present in your OpenShift Cluster
        - name: train-config-volume
          configMap:
            name: backend-service-train-config # This map is generated by Harness above

```
## Part 3: The Orchestration Layer (Harness UI)
Now, we hook everything up inside Harness so it knows what data to inject into <+env.variables.train_properties>.
### 4. Create your Environments in Harness
 1. Log into your Harness console and navigate to your **Project**.
 2. Go to **Environments** on the left menu.
 3. Create an environment for each of your trains (e.g., Train-Alpha, Train-Beta).
### 5. Add the Train-Wise Configurations
For **each** environment you just created, you need to add the environment variable that matches our YAML placeholder:
 1. Click into the **Train-Alpha** environment.
 2. Go to the **Variables** tab and click **+ Add Variable**.
 3. Set the name to train_properties and change the type to **Multi-Line Text**.
 4. In the value box, paste the configuration values specific to Train-Alpha:
   ```properties
   feature.new-ui-enabled=true
   database.name=alpha_db_schema
   
   ```
 5. Save it, then repeat the exact same steps for **Train-Beta**, but change the values to match the Beta train:
```properties
   feature.new-ui-enabled=false
   database.name=beta_db_schema

```
## How It All Works at Runtime (The Big Picture)
 1. **You trigger a deployment** in Harness targeting the Train-Alpha environment.
 2. **Harness reads your files:** It takes your configmap.yaml, looks at <+env.variables.train_properties>, pulls the specific text block you saved inside the Train-Alpha settings, and renders a complete manifest.
 3. **Harness pushes to OpenShift:** It runs oc apply behind the scenes to update the resources in your OpenShift namespace.
 4. **OpenShift spins up the Pod:** OpenShift looks at the deployment.yaml, creates two virtual folders inside your container (/config/cluster and /config/train), and fills them with the respective file content.
 5. **Spring Boot boots up:** Your Java app starts, sees the spring.config.import rule, reads the global properties from the cluster, overlays the custom properties from the train, and fully configures your Application Context seamlessly!
